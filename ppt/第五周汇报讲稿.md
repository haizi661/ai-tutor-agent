## 5. `data/` 目录重点解释
```text
data/
├─ knowledge/                 # 原始知识文件，放 PDF / md / txt
├─ chroma_db/                 # Chroma 持久化向量库
│  ├─ chroma.sqlite3          # Chroma 元数据
│  └─ <uuid>/                 # 向量索引二进制文件
├─ knowledge_index.json       # 文件指纹 + chunk 数
├─ bm25_cache.json            # BM25 缓存，避免每次完全重建
├─ retrieval_state.json       # 当前 embedding / chunk 配置状态
└─ tutor_memory.db            # SQLite，会话历史与流程 checkpoint
```

建议重点解释：
1. `knowledge/` 放的是原始资料，不参与检索计算本身。
2. `chroma_db/` 才是真正的向量检索库，里面保存 chunk、metadata 和 embedding。
3. `knowledge_index.json` 不存正文，只记录文件指纹和块数，用来判断文件是否变化、是否需要重新解析。
4. `bm25_cache.json` 是基于现有 chunk 构建出的关键词索引缓存，用来加速重启。
5. `retrieval_state.json` 记录当前使用的 embedding 模型和切块配置，配置变了就触发安全重建。
6. `tutor_memory.db` 存的不是知识块，而是聊天线程、checkpoint 和恢复状态。

口播建议（55秒）：
`data/` 这一层其实特别关键，因为它体现了我们把“知识内容”和“会话状态”分开管理。`knowledge/` 只放原始文件；`chroma_db/` 负责向量检索；`bm25_cache.json` 负责关键词检索缓存；`knowledge_index.json` 和 `retrieval_state.json` 负责判断什么时候该重建；而 `tutor_memory.db` 单独存会话历史和恢复点。这样分层的好处是，知识库重建不会影响聊天状态，聊天恢复也不会污染知识检索。

## 6. BM25 与 Chroma 混合架构怎么用
```text
用户问题 / 学习主题
  ▼
query_with_sources()
  ├─ Chroma: 做语义相似度检索
  ├─ BM25:   做关键词匹配检索
  ├─ metadata boost:
  │    对文件名、标题、section 做额外加权
  ├─ RRF 融合:
  │    合并两路结果并重排
  └─ citation gate:
       只有高置信命中才展示参考来源
  ▼
返回 context + citations
  ▼
tutor 节点组织成最终回答
```

需要讲清的点：
- Chroma 解决的是“换种说法也能搜到”的问题。
- BM25 解决的是“关键词、术语、文件名精确匹配”的问题。
- 两者不是二选一，而是针对同一批 chunk 建两套索引。
- Chroma 更偏语义，BM25 更偏词面，RRF 负责把两边结果融合。
- 我们又补了文件名和标题匹配增强，所以像“3403使用指南”这种查询会优先命中对应文件。

口播建议（55秒）：
我们现在不是只做向量检索，也不是只做关键词检索，而是把两者结合起来。Chroma 擅长理解语义，适合处理“用户换种说法提问”；BM25 擅长抓术语、标题和文件名，适合做精确匹配。最终我们用 RRF 做融合，再加一层文件名和标题的 boost，所以这套架构更适合真实教学场景，而不是只在单一问法下有效。

## 7. 当前实际使用方式
- 入库阶段：
1. 扫描 `data/knowledge/`
2. 判断文件指纹是否变化
3. PDF 优先走 MinerU，失败则回退本地 PyMuPDF
4. 生成 chunk，写入 Chroma
5. 再从 Chroma 重建 BM25

- 查询阶段：
1. `tutor` 节点收到学习主题或问题
2. 走 `query_with_sources()`
3. 取回混合检索结果
4. 将结果拼成 context
5. 大模型基于 context 生成讲解

口播建议（35秒）：
所以系统的实际运行方式可以分成两个阶段：第一个是入库，把资料变成可检索的 chunk；第二个是查询，把用户问题映射到最相关的 chunk，再让模型基于这些 chunk 生成答案。也就是说，大模型不是裸答，而是先查再答。

## 8. 本周遇到的问题与解决
- 问题1：MinerU 云端解析虽然完成，但返回 zip 下载阶段失败
  - 表现：Step 3 显示 `DONE`，但 Step 4 出现 SSL EOF
  - 原因：WSL + 代理环境下，CDN 域名解析被 fake-ip 污染
  - 解决：
    1. 增加 SSL / ConnectionError 重试
    2. 连续失败后自动切 `direct`
    3. 再失败时走项目内 DoH 公共 DNS 绕过
    4. 最终仍失败时回退本地 PyMuPDF

- 问题2：引用展示过于生硬
  - 表现：只要检索到东西就直接挂参考来源
  - 解决：加 citation gate，只有高置信命中才展示引用

- 问题3：中文文件名查询不稳定
  - 解决：更换多语 embedding，并增加文件名 / 标题 boost

口播建议（55秒）：
本周最大的工程问题不是模型本身，而是 PDF 云端解析后的结果下载。前面上传和轮询都成功了，但下载结果包时 CDN 这一步在 WSL 环境里出现了 fake-ip 干扰。我们最后不是简单地把功能关掉，而是做了重试、直连切换、公共 DNS 绕过和本地回退四层保护。这样即使网络有问题，知识库也不会彻底不可用。

## 11. 备答题
### 1. 为什么要同时用 Chroma 和 BM25？
- 回答：因为语义检索和关键词检索各有短板。只用 Chroma，文件名和术语匹配不稳定；只用 BM25，换种表达就容易漏召回。混合后更适合真实教学问答。

### 2. `data/` 里面为什么放这么多文件？
- 回答：因为不同文件负责不同职责。原始文件、向量索引、关键词缓存、重建状态、会话历史不能混在一起，否则后续无法维护。

### 3. 为什么 MinerU 成功了还会失败？
- 回答：云端解析成功只代表服务端任务完成，不代表本地一定成功拿到结果 zip。我们遇到的问题就在下载阶段，所以后来补了 DoH 绕过和本地回退。
