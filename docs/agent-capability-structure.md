# 智能体能力新结构（独立草案）

> 目的：这是一个新的、独立的能力结构草案，用来整理智能体应该具备的能力边界、协作方式和验收标准。本文档不修改当前代码结构、运行链路、前端结构或已有工作流。

## 1. 总原则

### 1.1 不碰正在改的结构

- 不修改现有主流程节点、状态结构、前端信息架构、API 合约或知识图谱结构。
- 不在未授权情况下重排现有文件、抽象现有模块、迁移目录或替换运行入口。
- 如需验证能力，只能通过只读审查、独立文档、独立测试草案或新建隔离目录完成。

### 1.2 新结构必须隔离

新增能力结构应满足：

- 与当前业务结构解耦；
- 先文档化，再授权实现；
- 先定义能力契约，再讨论接入点；
- 默认不接入生产链路；
- 所有修改都应能被单独删除而不影响当前主结构。

### 1.3 智能体只做结构级辅助

智能体工作的目标不是“多写代码”，而是：

- 明确能力边界；
- 发现结构风险；
- 提供可验收的改造切片；
- 防止局部测试通过但总体目标没达成；
- 保护用户正在进行的结构调整。

## 2. 能力分层

建议把智能体能力分成 6 层，每层只对上层暴露稳定契约。

```text
agent_capabilities/
  00_principles/        # 协作原则、边界、禁止事项
  10_observation/       # 只读观察：扫描、比对、风险发现
  20_planning/          # 计划生成：任务拆分、验收标准、影响面
  30_artifact_design/   # 产物设计：文档、接口草案、测试草案
  40_execution_guard/   # 执行保护：变更范围、冲突检测、回滚策略
  50_verification/      # 验证：结构级验收、证据收集、未验证项
```

这个目录目前只是建议结构；除本文档外，尚未创建代码目录。

## 3. 能力模块定义

### 3.1 Observation：只读观察能力

职责：

- 读取项目文档、测试、现有结构；
- 对比用户目标和当前结构；
- 找出冲突、重复、缺口、风险；
- 输出事实，不做修改。

禁止：

- 自动修复；
- 自动重构；
- 自动调整流程；
- 在用户正在编辑的区域写入。

产物：

- observation report；
- changed-file inventory；
- risk map；
- ownership boundary。

### 3.2 Planning：计划能力

职责：

- 把用户目标转成结构级计划；
- 标注哪些是新结构、哪些会触碰旧结构；
- 明确需要授权的步骤；
- 给出最小可验收切片。

计划必须包含：

- 原始目标复述；
- 当前结构是否已经接近目标；
- 新结构的隔离边界；
- 不修改清单；
- 验收标准；
- 风险和回退方式。

### 3.3 Artifact Design：产物设计能力

职责：

- 新建独立文档；
- 新建接口草案；
- 新建测试草案；
- 新建不接入主链路的 demo 或 prototype。

默认产物位置：

```text
docs/agent-capability-*.md
sandbox/agent-capabilities/*
tests/agent_capability_contracts/*
```

注意：如果这些目录不存在，先询问或只创建明确授权的文件。

### 3.4 Execution Guard：执行保护能力

职责：

- 在任何写入前检查 git diff；
- 区分用户改动、智能体改动、未知改动；
- 只修改智能体自己创建或用户明确点名的文件；
- 发现冲突时停止。

执行前检查：

```bash
git diff --name-only
git status --short
```

写入规则：

- 新结构优先新文件；
- 不覆盖现有结构；
- 不做跨文件大规模 patch；
- 不把“顺手修复”混入任务。

### 3.5 Verification：验证能力

职责：

- 验证产物是否满足原始目标；
- 验证是否越界改动；
- 验证是否仍有未确认假设；
- 输出结构级结论，而不是只报测试通过。

验收输出格式：

```text
目标对照：...
已完成：...
未触碰：...
证据：...
风险：...
下一步需要授权：...
```

## 4. 新结构与现有项目的关系

### 4.1 当前阶段不接入运行链路

本文档定义的是“智能体协作能力结构”，不是 ai-tutor-agent 的业务结构。当前不建议接入：

- LangGraph 节点；
- API session；
- frontend UI；
- knowledge_map；
- student_state；
- 当前测试主套件。

### 4.2 未来可能接入点

只有当用户明确授权后，才考虑以下接入：

- 把 Observation 变成只读 CLI；
- 把 Planning 变成 docs/plans 模板生成器；
- 把 Execution Guard 变成 pre-edit checklist；
- 把 Verification 变成结构验收报告生成器。

## 5. 智能体工作协议

### 5.1 每次开始前

智能体必须先回答：

1. 本次任务是在新结构里做，还是要碰现有结构？
2. 哪些文件是用户正在改的，不能碰？
3. 是否需要先只读观察？
4. 输出物应该是文档、草案、测试草案，还是代码？

### 5.2 如果用户说“创建新的结构”

默认动作：

- 新建独立文档或隔离目录；
- 不修改现有业务代码；
- 不改已有前端/API/状态结构；
- 不把草案接入运行链路。

### 5.3 如果用户说“不要改现在的结构”

默认动作：

- 立即停止对现有结构文件写入；
- 只允许改智能体刚创建的文件；
- 如果需要撤回越界改动，先列清单，再只撤回确定属于智能体的改动。

## 6. 最小新结构建议

第一步只需要一个轻量结构：

```text
docs/
  agent-capability-structure.md   # 本文件：能力结构草案
```

第二步如需继续扩展，再新增：

```text
docs/agent-capability-contract.md       # 能力输入输出契约
docs/agent-execution-guard.md           # 写入边界和冲突保护规则
docs/agent-verification-template.md     # 结构级验收报告模板
```

第三步才考虑：

```text
sandbox/agent-capabilities/
  README.md
  observation_checklist.md
  planning_template.md
  verification_template.md
```

## 7. 当前建议

现在最安全的推进方式是：

1. 保持当前 ai-tutor-agent 业务结构不变；
2. 只在 docs 中建立智能体能力结构说明；
3. 等用户确认后，再决定是否创建 sandbox/agent-capabilities；
4. 任何代码化实现都必须另行授权。
